## Phase 5: フォトライブラリへの保存

### 実装

- `src/platform/photoLibrary.ts`：端末側への保存をプラットフォーム別に実装
  - iOS/Android（ネイティブ）：`@capacitor-community/media` の `savePhoto` で
    カメラロールへ直接保存。アルバム未指定にすることで、iOS 14+ では
    「追加のみ」権限で済む（必要最小限の権限）
  - Web/PWA：ブラウザのダウンロードとして保存
    （Android はダウンロード先がギャラリーに取り込まれる。
      iOS Safari はファイルApp に保存される）
  - iOS Safari から写真Appへ入れる唯一の方法は共有シートのため、
    記録詳細の「端末に保存」で `navigator.share({files})` を使う
- 保存失敗は記録の保存を巻き戻さない（記録が主、端末コピーは従）
- `src/settings.ts`：端末保存のON/OFF設定（localStorage、写真は保存しない）

### テスト

- `photoLibrary.test.ts`：Webダウンロード／共有シート／共有不可時の
  フォールバック／共有キャンセル／**記録削除が端末側の写真に触れないこと**

### 問題点（プラットフォーム制約）

- Web/PWAから「写真App（カメラロール）」へ直接書き込むAPIは存在しない。
  そのためWebでは「ダウンロード」＋「共有シート」が上限となる
- iOS Safari の共有はユーザー操作から直接呼ぶ必要があるため、
  撮影時の自動保存ではなく記録詳細の明示的なボタンとして提供する

### 次Phaseへの引き継ぎ

- 記録詳細画面に「端末に保存」ボタンを置く（Phase 7で実装）

### 実装

  - `photos/<photoFileName>`

  - fflateのストリーミングZipを使い、写真は1枚ずつ処理して
    メモリピークを抑える。JPEGは再圧縮せず格納（ZipPassThrough）
  - 進捗（何枚目か）を画面に表示
- 受け渡し `src/export/deliver.ts`
  - Web：ダウンロード
  - iOS/Android：キャッシュに書き出して共有シートへ

### テスト

## v1.0後の改善: 撮影を1:1に統一

### 背景

ビューファインダーが画面いっぱい（実質16:9）なのに対し、
保存される写真はカメラが返すストリームの比率のままで、見えている範囲と
保存される範囲が一致していなかった。

### 実装

- `centeredSquareCrop()` を追加し、`encodeFrame()` が既定で中央の正方形を切り出すようにした
  - ビューファインダーの `object-fit: cover` と同じ切り出しなので、
    **枠に見えている範囲＝保存される範囲** になる
  - ファイル選択のフォールバックで取り込んだ画像も同じ扱い
- `getUserMedia` の要求解像度を 1920x1920 から 1920x1440（4:3）に変更
  - 正方形は短辺基準で切り出すため、16:9より4:3のほうが画素を多く残せる
- 撮影画面のレイアウトを変更
  - 上部にPictaのアイコン（`PictaMark`）と文字を表示するヘッダー
  - その直下に1:1のビューファインダー
  - 余白は下側に寄せ、シャッターは画面下部に固定（端末の正方形モードと同じ配置）

### テスト

- `centeredSquareCrop` の単体テスト4件（横長・縦長・正方形・上限）
- カメラ画面：ヘッダーのアイコンと文字、1:1枠の存在
- E2E：ビューファインダーが1:1であること、**保存された写真も1:1**であること
- 単体・画面テスト 83件成功 / E2E 21項目成功

### 動作確認

- 擬似カメラのストリーム 1920x1440 → 枠 390x390 → 保存画像 1440x1440
- 390x844 と 360x640 の両方でヘッダー・枠・シャッターが収まることを確認

## v1.0後の改善: 撮影日時と撮影地点（EXIF）

### 背景

「EXIFの日付と場所が欲しい」という要望。ただし `getUserMedia` + canvas で
生成した画像には **EXIFが一切付かない**（canvas出力にメタデータは残らない）。
そのため「EXIFを読む」のではなく、日時と位置を自前で取得して記録し、
書き出すJPEGにEXIFとして**書き込む**方針で実装した。

### 実装

- `src/capture/exif.ts`：依存ライブラリなしのEXIF読み書き
  - 読み：APP1/TIFF/IFDを辿り `DateTimeOriginal`・`OffsetTimeOriginal`・
    `DateTime`・GPS緯度経度（度分秒＋Ref）を取得。壊れた入力は `{}` を返す
  - 書き：IFD0 / Exif IFD / GPS IFD を組み立ててAPP1として SOI 直後に挿入。
    既存のAPP1は置き換える（二重に付けない）
- `src/capture/geolocation.ts`：Geolocation APIのラッパー
  - 拒否・タイムアウト・非対応はすべて `null`（例外にしない）
  - `maximumAge: 60s` で直近の測位を再利用

## v1.0後の改善: メモを写真のキャプションに書き込む

### 調査

「キャプション」に当たるフィールドは1つではなく、日本語が確実に残るものは限られる。

| フィールド | 文字コード | 判断 |
| --- | --- | --- |
| EXIF `UserComment` | 8バイトの文字コード前置（`UNICODE\0` = UTF-16） | 採用。EXIF標準で日本語を扱える |
| XMP `dc:description` | UTF-8 | 採用。写真アプリが「説明」として表示するのはここ |
| EXIF `ImageDescription` | 宣言なし（ASCII前提で読まれる） | ASCIIのメモのときだけ採用 |
| IPTC `Caption-Abstract` | — | 見送り（APP13/Photoshop IRBが必要で、XMPと役割が重なる） |

`ImageDescription` にUTF-8を書いた場合の挙動をPillowで実測したところ、
latin-1として解釈され文字化けした。化けた文字を残すより空のほうがましなため、
ASCIIのメモに限定した。

### 実装

- `withExif` がEXIFとXMPの2つのAPP1セグメントを書くようにした
  - 既存のEXIF/XMPセグメントは走査して除去してから書き直す（積み重ならない）
  - `UserComment` は `UNICODE\0` + UTF-16LE（TIFFのバイト順に合わせる）
  - XMPは `dc:description` のみの最小パケット。XMLエスケープあり
- 読み側も対応：`UserComment`（前置の文字コードを見て復号）と
  `ImageDescription` を読み、ファイル選択で取り込んだ画像のキャプションを
  メモの初期値にする
- ASCII型タグの読み取りをUTF-8デコードに変更（ASCIIはその部分集合なので安全）
- メモを2000文字で切り詰める（APP1は64KBまで。サロゲートペアは割らない）
- **メモ・位置を編集したら保存済みの写真も刻印し直す**（`restampPhoto`）
  - タグだけの編集では書き直さない

### テスト

- `exif.test.ts` 25件：日本語・絵文字の往復、XMPの内容とエスケープ、
  ASCII/日本語での `ImageDescription` の出し分け、切り詰め、
  書き直しでセグメントが二重にならないこと、メモを空にすると消えること
- `db.test.ts`：メモ編集で写真のキャプションが追従／空にすると消える／
  位置削除でGPSも消える／タグだけの編集では写真を書き換えない
- `review.test.tsx`：保存した写真にメモがキャプションとして入る
- E2E：**ZIP内の写真に編集後のメモがキャプションとして入っている**こと
- 単体・画面テスト 129件成功 / E2E 30項目成功

### 独立検証（Pillow + defusedxml）

```
=== 日本語のメモ
```

## 不具合修正: 復帰後にカメラが止まったまま（前のコマが残る）

### 症状

アプリを起動（再開）したとき、たまに撮影画面が動かず、前に映っていた映像が
そのまま残る。

### 原因

カメラの取得が **マウント時／カメラ切替時／手動リトライ時にしか行われていなかった**。

- ホーム画面に追加したPWAを開き直すと、多くの場合ページは読み込み直されず
  復帰するだけなので、撮影画面のコンポーネントはマウントされたまま
- その間にOSはカメラを閉じている（通話・他アプリ・画面ロックなどでも起きる）
- `<video>` は最後に描画したコマを保持し続けるため、止まった絵が残る
- `status` は `ready` のままなので、UIも「動いている」ものとして表示していた

つまり再現性のある実装漏れで、環境依存の偶発事象ではない。

### 修正

- トラックの `ended` / `mute` / `unmute` を監視
  - `ended`：止まった表示にしてから取り直す
  - `mute` → `unmute`：一時的な中断なので取り直さず、表示だけ切り替える
- `visibilitychange` / `pageshow`（bfcache復帰）/ `focus` で生存確認し、
  死んでいれば取り直す
- どのイベントも飛ばない環境向けに、復帰後800msで `currentTime` が
  進んでいなければ凍結とみなして取り直す
- 取り直し中は `stalled` として映像を隠し、「カメラを再開しています…」を表示。
  シャッターとグリッドも無効にする（止まったコマを撮らせない）
- 権限拒否・カメラ非対応のときは自動で要求し直さない（許可ダイアログの連発を避ける）
- `play()` がPromiseを返さない環境向けに `safePlay` を追加

### テスト

- `cameraResume.test.tsx` 5件：
  カメラを取り上げられたときの表示と取り直し／`pageshow` での復帰／
  生きているときは取り直さない／中断中はシャッターを押せない／
  権限拒否後は勝手に要求し直さない
- E2E：実ブラウザでトラックを停止して `pageshow` を送り、

- 単体・画面テスト 141件成功 / E2E 37項目成功

## v1.0後の変更: 削除時に「端末の写真も消すか」を選べるように

### 調査（先に結論）

端末のフォトライブラリからの削除は、**プラットフォームによって可否が分かれる**。

| | 可否 | 根拠 |
| --- | --- | --- |
| Android（ネイティブ） | できる | `Media.savePhoto` が `filePath` を返すので、保存時に控えておき `Filesystem.deleteFile` で削除する（アプリが書き出した自分のファイル） |
| iOS（ネイティブ） | できない | 写真Appの写真の削除は PhotoKit の `PHAssetChangeRequest.deleteAssets` が必要。`@capacitor-community/media` のAPIは `savePhoto`/`saveVideo`/`getMedias`/`getAlbums` などで、削除は無い |
| Web / PWA | できない | ブラウザが自身のダウンロードしたファイルを削除するAPIは存在しない |

npm上で削除に対応した保守中のCapacitorプラグインも見つからなかった
（`capacitor-gallery-plus` は読み取り専用、`@capgo/capacitor-photo-library` は表示用）。

### 実装

- 保存時に端末側コピーの在処を記録に持たせた（`Record.libraryPhoto`）
  - iOS: PHAsset identifier / Android: ファイルパス
  - これが無いと、後から「どの写真か」を特定できない
- `deleteRecord` / `deleteRecords` に `alsoFromLibrary` を追加し、
  結果（削除できた件数・失敗件数・非対応かどうか）を返すようにした
- UIは単体削除・まとめて削除の両方を選択式に
  - 単体：「アプリ内から削除」／「アプリ内と端末の写真を削除」
  - まとめて：「メモだけ削除」／「アプリ内から削除」／「アプリ内と端末の写真を削除」
  - **できない環境では理由を添えて選べない状態で表示する**（黙って消さない・
    できないことをできるように見せない）
- 端末側の削除に失敗しても記録の削除は完了させ、件数を通知に出す

### 既知の制約

- **iOSとWebでは端末の写真を削除できない。** iOS対応には PhotoKit を叩く
  ネイティブプラグインの自作が必要（この環境ではXcodeが無く実装・検証ができない）
- **Androidの削除処理は実機未検証。** この環境にAndroid端末・SDKが無いため、
  配線（参照の記録→削除呼び出し→結果の集計）はモックで検証し、
  実際の削除可否は実機確認が必要
- アプリ更新前に保存した記録には `libraryPhoto` が無いため、
  端末側の写真は特定できない（「削除できず」として件数に出る）

### テスト

- `libraryDelete.test.ts` 6件：既定では端末に触れない／参照を使って削除する／
  失敗しても記録は消す／非対応環境でも記録は消して理由を返す／
  参照が無い記録／まとめて削除の集計
- `records.test.tsx`：単体・まとめての確認画面の選択肢、
  Webでは端末削除が選べず理由が出ること
- E2E：単体削除・まとめて削除の選択肢と、Webでの無効表示
- 単体・画面テスト 147件成功 / E2E 38項目成功

## v1.0後の追加: 保存データの保護と、端末保存OFF時の警告

### 背景

「端末にも保存する」をOFFにすると写真はアプリ内の1か所だけになる。
Webでは IndexedDB なので、端末の空き容量が減るとブラウザに削除されうる。
利用者がそれを知らないまま使うとデータを失うため、2点を追加した。

### 実装

- `src/platform/storage.ts`
  - `checkPersistence()` / `requestPersistence()` / `ensurePersistenceOnce()`
  - 状態は `native` / `persisted` / `not-persisted` / `unsupported` の4つ
  - ネイティブはアプリ専用領域のため申請不要（`native` を返す）
  - **自動要求は「最初の保存が成功した直後に一度だけ」**
    起動時にしないのは、Firefoxなどが利用者に確認を出すため。
    要求済みフラグは設定に保存し、二度は聞かない
- 設定画面
  - 「自動削除からの保護：保護されています／保護されていません」を表示し、
    未保護なら「データを保護する」ボタンを出す
  - 状態ごとに説明文を変える（ホーム画面に追加すると通りやすい、など）
  - 端末保存をOFFにすると、その場に警告を表示する
    （バックアップがZIPエクスポートだけになること）

## v1.0後の追加: fmt-jp/open への自動反映

### 背景

同じアプリを [fmt-jp/open](https://github.com/fmt-jp/open) のアプリ置き場でも
`torikoto/` として公開することにした。手作業でビルド成果物をコピーし続けるのは
確実に忘れるので、`main` への push で自動反映するようにした。

### 実装

`.github/workflows/publish-to-open.yml`

- ビルド前に型チェックとテストを通す（壊れたものを公開先へ配らない）
- `open` をチェックアウトし、**`torikoto/` だけ**を入れ替えて commit / push
  - 他のアプリや `index.html` には触れない
  - 差分が無ければ commit せず notice を出して終了
- `concurrency` で `open` への push が重ならないようにする

### トークンの扱い

別リポジトリへ push するため `GITHUB_TOKEN` では足りず、
`OPEN_REPO_TOKEN`（`fmt-jp/open` の Contents: Read and write）が要る。

**未設定でも失敗させない**設計にした。`secrets` は `if:` から直接参照できないため、
先行ジョブでシークレットの有無を出力に落とし、本体ジョブの `if:` で判定する。
未設定なら notice を出してスキップする（赤いバツを残さない）。

### 既知の制約

- `open/index.html` のアプリ一覧カードは自動更新しない（初回だけ手動）
- Pages へのデプロイとは別ワークフローにした。ビルドは二重になるが、
  `open` への同期が失敗しても Pages の公開は止まらない

### 追補: トークンの切り分けを足した

最初にシークレットを登録したとき、`actions/checkout` が
`Bad credentials` とだけ出して失敗した。既定ブランチ名を調べる REST 呼び出しが
401 を返していたが、ログからは「権限不足なのか、トークン自体が無効なのか」が
読み取れなかった。

- **ビルド前に `Check token`** を置き、`GET /repos/fmt-jp/open` の応答で
  401 / 403 / 404 / 書き込み不可 を切り分けて日本語で報告する
  （無効なトークンのままビルドを回さない）
- `Checkout open` に `ref: main` を明示し、既定ブランチ名を問い合わせる
  REST 呼び出し自体を不要にした

原因はトークン側（401 = トークンが認識されない状態）で、作り直して解決した。
その後の実行で、ビルド → コピー → **push** まで通ることを確認している。

### 実際の反映

```
d6f0c83  torikoto: picta 560314a を反映
905a5d1  torikoto: picta c7c556d を反映
```

変更されるのは `torikoto/` 配下だけで、`open/index.html` や他のアプリには
触れていない。コミットメッセージに元の picta のコミットが入るため、
どのバージョンが載っているか追える。

- はみ出さないよう、表示サイズから移動量を計算して制限する

## v1.0後の追加: ZIPからのインポート（復元）

仕様§24で「将来ZIPをインポートして復元できる構造にしておく」としていた部分の実装。
`manifest.json` にバージョンを持たせておいたことがそのまま効いた。

### 決めたこと

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 対象 | ZIPのみ（CSV単体は不可） | 写真の無い記録は成立しない |
| 重複 | 同じ `id` は**スキップ**（上書きしない） | 二度読んでも壊れない。手元の編集を消さない |
| 旧形式 | `picta-export`（version 1）も受け付ける | 改名前のバックアップを切り捨てない |
| 列 | 名前で引く（位置固定にしない） | version 1 に緯度経度の列が無いため。増減・並び替えにも強い |

### 実装

- `src/export/csvParse.ts`：RFC4180相当のCSV読み取り
  - 引用符・カンマ・改行・二重引用符を含む値を復元する（メモは全部入りうる）
  - BOMを除去。日時は `manifest.json` のオフセットで復元し、無ければ端末のローカル時刻
- `src/export/importZip.ts`
  - **ストリームで2回読む**。1回目は `manifest.json` と `records.csv` だけ、
    2回目で写真を1枚ずつ書き込む。全部をメモリに展開しない
    （400KB×500枚のバックアップを丸ごと抱えると端末が落ちるため）
  - チャンクの合間に書き込みを流すことで、保持するのは実質1枚分
  - `Blob.stream()` が無い環境（古いiOS Safari・jsdom）ではスライス読みに切り替える
  - 写真の寸法は**JPEGのフレームヘッダ（SOFn）から直接読む**。
    デコードを待たないので速く、環境にも依存しない（`jpegSize` を `exif.ts` に追加）
- UI：エクスポート画面に「インポート（復元）」。
  ファイルを選ぶと**まず内容を確認するダイアログ**を出し、承認後に実行する

### テスト

- `importZip.test.ts` 13件：CSV読み取り（引用符・改行・BOM・日時）、
  中身の確認だけでは何も変えないこと、全消し後の復元（メモ・日時・タグ・位置）、
  写真がバイト列のまま戻りEXIFも保たれること、タグの再登録、
  二度読んでも増えないこと、既存の編集を上書きしないこと、
  0件ZIP、ZIPでないファイル
- E2E：**エクスポート → 全件削除 → インポート**の往復。
  記録・写真・メモ・タグ・位置情報が戻ること、二度読んでも増えないこと
- 単体・画面テスト 173件成功 / E2E 45項目成功

## v1.0後の変更: メニューアイコンを自前の線画に

### 経緯

ハンバーガーメニューを開いたときのアイコンが絵文字（📷📚🔍🏷📤⚙）で、
写実的なうえ端末ごとに絵柄が変わるため、アプリの見た目から浮いていた。

アプリアイコンの配色（白のリング＋金のコア）をもとに4案をモックで出し、
**B案「白の線画＋金のアクセント1点」** を採用。

| 案 | 内容 |
| --- | --- |
| A | 白の線画のみ |
| **B（採用）** | 白の線画＋各アイコンに金のアクセントを1点 |
| C | 全体を金の線画 |
| D | 丸い座布団に載せる |

B はアプリマークそのものの作り（白のリング＋金のコア＋金の点）と同じ構成で、
一覧にしたときも金の点が視線の足がかりになる。

### 実装

- `src/ui/MenuIcon.tsx` を追加。24×24 の SVG を6種（撮影・記録・検索・タグ・
  エクスポート・設定）持つ。線は `currentColor` の 1.7px、金の部分は
  `var(--accent)`
- 重なりのあるアイコン（記録の写真2枚、設定のスライダー）は SVG マスクではなく
  **背景色で塗りつぶした図形**で手前を抜いている。塗り色は
  `--menu-icon-bg` 変数で、通常行は `--bg-raised`、選択中の行は `--bg-input` と
  行の地の色に追従するので、選択状態でも切り抜きが破綻しない
- `MenuDrawer.tsx` の `emoji` フィールドを `icon` キーに置き換え、
  `.menu-item .emoji` のCSSは削除

### テスト

- 単体を1件追加（全6項目に `svg.menu-icon` があり、線画クラスと金のアクセント
  クラスを両方持つ）。単体 **173件** 通過
- 実ブラウザで記録画面を開いた状態のメニューを撮影し、選択行の切り抜き色が

## v1.0後の変更: 通常ボタンを押せるものに見えるように

エクスポート画面で「CSVを書き出す」「ZIPを読み込む」が押せるものに見えない、
という指摘。原因は、通常ボタンの地色と枠線が、それが載っているカードと
まったく同じ（`--bg-raised` ＋ `--line`）で、輪郭がほぼ消えていたこと。

**「金＝その画面で一番やってほしいこと、1画面に1つ」** という配色ルールは
そのままに、通常ボタンだけを一段持ち上げた。

- 地色を `--bg-raised` → `--bg-input` に（カードより一段明るい）
- 枠線に `--line-strong: #43434d` を新設して使う
- 危険ボタンの枠線も同じ強さに合わせた（`#4a2626` → `#5c3131`）

`.button` の定義1か所だけの変更なので、エクスポート・記録詳細・タグ管理・
確認ダイアログなど通常ボタンを使う画面すべてに同時に効く。
金のボタン（保存する／ZIPを書き出す／ダイアログの実行）との差は保たれている。

実ブラウザでエクスポート・記録詳細・削除確認ダイアログを撮って目視確認。
単体173件・E2E45項目とも通過。

### 現状維持と決めたこと

利用者と相談のうえ、「軽量・シンプル・撮影中心」という方針から
**あえて手を入れていない**項目。

| 項目 | 現状 | 判断 |
| --- | --- | --- |
| 解像度 | 短辺基準の正方形・上限2048px（実機で概ね1440×1440） | `getUserMedia` は写真用センサーのフル解像度を返さない。要求値を上げても端末依存で効果が読めず、容量とのバランスも今が妥当 |
| フォーカス | OSのオートフォーカス任せ（`focusMode` / `pointsOfInterest` を指定しない） | タップAFはiOSでほぼ効かず、中央固定も端末依存。端末依存の制御を増やさない |

### 積み残し

- **iOS / Android の実機ビルドは未実施**（この環境にXcode/Android SDKが無い）。
  ネイティブ実装と権限設定は用意済み
- **端末フォトライブラリからの削除**は Web / iOS で不可。
  Androidネイティブ向けの実装はデータ層に残しているが、UIには出していない（実機未検証）
- ~~ZIPからのインポート（復元）~~ → 対応済み（上記エントリ）
- トークン（`OPEN_REPO_TOKEN`）の有効期限が切れると `open` への同期が止まる。
  そのときは `Check token` が 401 で失敗して気づける
